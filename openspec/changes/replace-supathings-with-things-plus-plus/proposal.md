# Proposal

## Problem

The active Things integration is a single third-party `supathings` MCP server mixed into generic MCPHub groups. Its 37-tool surface is useful, but it is not a complete or sufficiently isolated Things capability: it couples read access to one implementation, exposes raw URL/JSON-shaped operations, lacks an authenticated ChatGPT contract, and leaves the portable `things-manager` skill tied to SupaThings-specific names.

Replacing it piecemeal could silently contract coverage. The migration therefore needs one auditable capability closure across MCP servers, the semantic skill, generated harness projections, OAuth/tunnel policy, docs, and live runtime state. OpenSpec is required because the change alters public tool contracts, MCPHub topology and validation, a portable skill and its eval corpus, multiple generated surfaces, and local/remote rollout and rollback behavior.

## Intent

Build Things++ as a root-bundle capability with these locked outcomes:

1. Keep the repository root plugin as the sole plugin and skill source of truth; do not create a nested Things plugin or duplicate `skills/`, `mcp/`, or instruction trees.
2. Replace active SupaThings routing with exactly one MCPHub group named `things`. Local Codex and remote ChatGPT both use `/mcp/things`; there is no `things-chatgpt`, `things-admin`, generic-group membership, enabled client-facing individual Things server route, or alternate public Things endpoint.
3. Freeze the MCPHub basis to the exact signed `@samanhappy/mcphub@1.0.32` tarball identity recorded below and an exact transitive dependency lock. The registry signature and provenance are public evidence, not substitutes for the independently hashed tarball, immutable lock, owned-source inventory, or patch audit.
4. Build a repository-owned, content-addressed downstream distribution in `mcp/mcphub/downstream/`. A retrospective migration note counted six whole-module replacements and five guarded patches, but it did not freeze their identities, anchors, preimages, postimages, or outputs and is therefore non-authorizing historical evidence rather than a seal prerequisite. Before materialization, freeze a fresh exact owned-source/replacement/patch inventory that includes every v2-boundary module and every production-loaded file. The materializer verifies the tarball, exact transitive lock, dependency graph, complete current inventory, deterministic build-time transformations, outputs, output-inventory receipt, and aggregate digest receipt before atomically publishing one digest-addressed runtime. An unlisted, unhashed, or changed production file fails closed. The launcher loads only that downstream in the same Node process; production has zero loader transformations and does not use `npx`, a live registry fetch, ranged resolution, mutable cache, live patching, `NODE_OPTIONS`, or the legacy ESM loader/patch hook.
5. Keep two distinct loopback trust origins for the same logical group and exact path: `http://127.0.0.1:46683/mcp/things` is local-bearer-only, while `http://127.0.0.1:46684/mcp/things` is OAuth-only and may be reached only by cloudflared for public resource `https://mcp.w4w.dev/mcp/things`. These are lifecycle-separated origins, not listeners that local activation starts together: S3 binds only managed `46683` with remote mode disabled and no `46684` listener, tunnel, or capture receipt; the local listener may expose the exact 70-tool schema/catalog even when an absent fixed Shortcut bridge or unproved TCC makes an affected call return a typed unavailable/degraded result. Such degradation never authorizes a raw, direct-database, or UI-automation fallback and is not evidence that the affected operation is usable. The 2026-08-28 continuation explicitly authorizes the S4 remote implementation and apply sequence, but does not waive its gates: S4-02 is the first gate that may bind a restricted loopback-only, tool-dispatch-disabled `46684` capture listener after offline conformance and fresh bridge/TCC proof; S4-04 is the first gate that may bind production/public `46684` after the content/config/route-manifest-bound final activation receipt. Neither listener accepts the other credential class or derives listener identity from caller-controlled forwarding headers.
6. Compose three internal MCPHub members behind the single group:
   - `things-core`: all 41 tools from the pinned `mcp-server-things==1.9.0`, mediated by a security adapter without changing their Things semantics;
   - `things-shortcuts`: 21 closed, typed Things Shortcuts operations;
   - `things-native`: 8 fixed official native operations—one static health tool, one repository-owned `things:///search` URL builder, and six static/fixed AppleScript operations.
7. Freeze the qualified capability union at exactly 70 unique operations (`41 + 21 + 8`) as enumerated in `capability-manifest.json`. Any tool name, schema, count, mapping, or public qualification change requires an explicit revision to this active OpenSpec change before generation or activation.
8. Prove coverage expansion, not just process replacement: map all 37 SupaThings outcomes, all 17 current `things-manager` workflows, and all 25 legacy eval concepts to the new stack with zero loss, and require at least one independently tested net-new Things outcome.
9. Rewrite `things-manager` as the portable Things++ semantic/router/safety layer and expand its eval corpus to 41 cases: 25 rewritten concepts plus 16 additive cases.
10. Use built-in same-process MCPHub OAuth only, with approved Client ID Metadata Documents (CIMD) as the primary ChatGPT identity and strict DCR only when current redacted observed wire and user-owned app readback select it. Require PKCE S256, exact resource/audience/principal/redirect/scope binding, RFC 9207 issuer identification, and three independent `things.read`, `things.write`, and `things.admin` scopes. Persist opaque authorization state in a separate owner-only SQLite database that stores only state/code/token/DCR-secret/JTI hashes and public authorization metadata, never private Things content. Keep remote access disabled until the complete digest-bound OAuth suite, callback approval, and current observed-wire gate pass.
11. Expose the public service through ordered, deny-by-default Cloudflare ingress and support exactly two stateless MCP eras on the same `/mcp/things` route: modern `2026-07-28` with `server/discover`, matching header/body metadata, and no initialization; and legacy `2025-11-25` with compatibility `initialize`. Neither era mints, requires, persists, or echoes an MCP session, and an invalid modern request never falls back to legacy. Freeze the exact methods, paths, status codes, protocol headers, OAuth endpoints, authenticated `GET`/`DELETE` `405` behavior, and normalized cross-era 70-tool catalog in one versioned route/conformance manifest. Current OpenAI documentation does not prove ChatGPT's emitted era or registration mode, so remote enablement also requires a redacted current observation rather than an inferred transport assumption.
12. Make runtime rollback an atomic binary/config pointer operation between verified content-addressed distributions and exact configuration snapshots. The OAuth SQLite database is never included in, replaced by, or restored from rollback material, so rollback cannot resurrect consumed, expired, or revoked credentials. Preserve the dirty `main` worktree, archived evidence, and unrelated edits; do not create a branch, commit, push, install skills live, construct Shortcuts through uncontrolled UI automation, create an external ChatGPT app/Project, or mutate Things data without the corresponding explicit gate.
13. Treat the first live cutover as failed operational evidence, not as activation proof. That selected seal authenticated and materialized, but MCPHub 1.0.32 eagerly initialized the full preserved server topology before binding; an unrelated DeepWiki preflight resolved to public `100.23.203.190` and hit an upstream RFC 6598 range bug, so startup failed before any listener bound. The clean rollback restored the prior verified pointer/config state, left remote/tunnel mode disabled, and left no failed-selection listener behind. Recovery authorizes exactly two deterministic build-time corrections against exact upstream preimages: replace malformed `[0x64000000, 0x657fffff]` (`100.0.0.0`–`101.127.255.255`) with RFC 6598 `[0x64400000, 0x647fffff]` (`100.64.0.0`–`100.127.255.255`), and contain each server's awaited URL/transport preflight so one rejected backend is recorded as enabled-but-disconnected with a sanitized error while initialization continues. Neither correction weakens SSRF rejection, removes or disables an unrelated server, narrows runtime settings to Things, creates an alternate Things group, or permits a production-loader transformation. The failed digest `sha256-7369fbfd45eebe415500d41cbb9de5c55b2d95338932344ed09820d7e72a7262` and historic quarantined digest `sha256-bda99d286dd44377d37a7c9500fea8d3f9005c426c59ce92b4a0018bebce0182` are frozen in the shared distribution-revocation registry; selector and launcher paths reject either identity before pointer/receipt writes or distribution-byte reads. All downstream manifests, outputs, receipts, digests, and materializations become stale when either correction changes and must be rebuilt, independently checked without selecting `current` or binding a listener, resealed to a non-revoked digest, rematerialized, and then re-run through the local live gates before any remote gate.
14. Continue the migration through the now-authorized S4 remote implementation, restricted apply, and F5 assurance sequence without weakening any fail-closed gate. Source implementation, offline conformance, capture, observed-wire, production activation, external route proof, and ChatGPT UI readback remain distinct proof layers. Missing fixed bridges, noninteractive TCC readiness, an authenticated ChatGPT observation, or UI access is a reported blocker for that layer—not a lack of authorization and not evidence that the layer passed. `TPP-CLOSE` requires authoritative results for every runnable layer and an exact blocked/unrun disposition for evidence that cannot be obtained in the current environment.

## Scope

- First-party server/adaptor source declarations bounded to `fastmcp>=3.4.7,<4` for the core, closed Things Shortcuts, and fixed native operations, with typed schemas and tests; the frozen root lock and verified runtime resolve exact FastMCP `3.4.7` wherever that runtime is imported.

## Out Of Scope

- A nested Things plugin, new agent definition, second root manifest, or duplicated portable skill tree.
- `things-ui`, `thingskit`, a second CRUD implementation, any direct read or write of the Things database, or a non-MCPHub authorization server. A separate hardened SQLite database containing only hashed opaque OAuth state and authorization metadata is explicitly permitted and is not a Things database integration.
- Arbitrary Things URL, raw JSON, generic Shortcut execution, arbitrary AppleScript, shell, filesystem, SQL, or uncontrolled UI automation.
- Recurrence-template editing or deterministic positional reordering; both remain explicitly unsupported until an audited backend exists.
- Compatibility aliases for SupaThings or old group names in active config. Rollback uses verified binary/config pointers and exact config bytes; it excludes OAuth and receipt databases and cannot restore credential usability.
- Live mutation tests, Shortcut construction/import, global skill sync/install, Cloudflare enablement, or ChatGPT app/Project creation before their explicit gates.
- Force-push, history rewriting, broad staging, or publishing without post-push readback. Atomic conventional commits and a non-force push are explicitly authorized for this continuation after validation and exact-path staging.

## Affected Users And Tools

- Codex and other opt-in local MCP clients consume one loopback `mcphub_group_things` projection. Repo generation is blocked until repo-only sync performs no home/private fallback reads, regenerates the sanitized Codex and OpenCode MCP surfaces, and retains Cursor's disabled opt-in projection.
- ChatGPT consumes the same logical group only through `https://mcp.w4w.dev/mcp/things` after built-in OAuth, observed-wire, dual-era, and tunnel conformance; the OAuth-only origin remains `http://127.0.0.1:46684/mcp/things`.
- Things 3 users retain every audited SupaThings outcome and gain typed checklist, bulk-create, native tag/area administration, selection, duplication, and structured-project operations.
- Maintainers gain deterministic capability-closure, SupaThings-absence, group-topology, auth, rollback, and proof-layer checks.

## Generated Surfaces To Refresh

- Root portable/native plugin artifacts and the native `things-manager` adapter projection.
- README, skill catalog index and pages, skill research pages, MCPHub/operator pages, and the web production build.
- Runtime settings and home harness configs only after source validation, exact backups, dry-run/readback, and the live-apply gate.

## Risks

- The upstream core is beta and can expose token-bearing Things URLs; the immutable pin, adapter, and redaction tests are release blockers.
- The published MCPHub package is a compiled distribution without its TypeScript source or a full transitive lock. A valid registry signature cannot establish the downstream patch graph; exact tarball, dependency-lock, owned-source, patch-manifest, and materialized-runtime digests are all release blockers.
- Six native AppleScript operations and the fixed Shortcuts bridges cross macOS TCC boundaries; the F0 observation found both fixed Shortcuts absent and TCC readiness unproven. Source work and local bearer schema/catalog activation may proceed, but each affected call must return a typed unavailable/degraded result until fresh prerequisite proof succeeds; no operational claim or fallback is allowed. Remote/public activation remains blocked until the bridge/TCC prerequisites and every remote gate pass. The static `native_health` tool performs no AppleEvent, and the fixed `open_search` URL builder accepts only a query and never a caller-provided URL.
- The current runtime evidence is temporally inconsistent/stale and cannot support cutover; provenance must be refreshed immediately before cutover.
- Built-in MCPHub OAuth and the v2 edge require exhaustive current closure. Treating the unfrozen retrospective six-plus-five count as authorizing evidence, omitting a v2-boundary module, admitting an unspecified production file or loader transformation, materializer drift, credential-class confusion, issuer/client-mode substitution, or cross-route token replay is fail-closed. Remote access remains disabled until the freshly inventoried content-addressed downstream, dual-era route manifest, CIMD/DCR policy, and current observed-wire evidence pass end to end.
- A single full-capability group exposes destructive tools to authenticated clients. Accurate annotations, least-scope enforcement, per-tool client approval, preview/confirmation, and audit-safe receipts are mandatory.
- Shared registry, lockfile, generated outputs, home configs, and runtime processes are collision-prone in the current dirty worktree; they require serialized ownership and exact rollback snapshots.
- A 70-tool model-facing surface has schema cost. The user explicitly prefers coverage expansion; the single opt-in group contains the full audited union while the default `harness` group remains unchanged.
- A valid content seal can still be operationally unfit. The first cutover proved that upstream MCPHub eagerly preflights unrelated enabled servers before listener bind and has no native group-scoped first-start API. Removing DeepWiki, shrinking runtime settings, or weakening the SSRF policy would hide the failure by contracting the existing topology. Recovery therefore preserves every non-Things server/group, keeps all Things logic behind the sole `things` group, isolates a failed server transport without dispatching it, mechanically revokes both known unsafe distribution identities, and makes a fresh non-revoked reseal, isolated no-bind startup proof, rematerialization, and fresh local live readback mandatory.
